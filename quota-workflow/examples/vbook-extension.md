# Worked example: vBook extensions (illustration only)

> This is an EXAMPLE of the `quota-workflow` skill applied to one project.
> It is not part of the skill core. The core is generic; this file only
> shows how the "project adapter" looks when the project is a vBook
> extension repo.

## The task (2026-11-07)

Build new novel-source extensions for the vBook app and push them to the
repo `qsang2025/Qsang_vbook` (public, branch `main`). Three Chinese sites
were picked from a ranked shortlist: sto9.com, czbooks.net, shuhaige.tw.

## Project adapter (what was filled in for this project)

- **Repo:** https://github.com/qsang2025/Qsang_vbook, branch `main`.
- **House rules file:** `AGENTS.md` in the repo root — extension work uses
  `.agents/skills/vbook-extensions/SKILL.md` plus exactly one mode file;
  `extension-api.md` is the single contract (two identical copies, keep
  md5-matched); `src/` is the single source of truth; the registry
  (`plugin.json`) is generated by `build-catalog`, never hand-edited;
  test/build/install only via `scripts/cli.js`; `config.js` is required;
  full lifecycle home/genre/search/detail/toc/chap (+ `page` when the TOC
  is paginated); use `Response.error` with Vietnamese messages instead of
  `return null`.
- **Constraints:** do not touch `.github/workflows/*` (the git token has no
  `workflow` scope — workflow files must go through the web UI); pull
  --rebase before pushing; `plugin.zip` is committed and validate requires
  it to byte-match the on-disk `src/`.
- **Verified facts used in the plans:** each site's URL patterns, chapter
  content location, and bot protection — verified by curl + on-device
  testing before building (e.g. sto9's full TOC lives at an AJAX endpoint
  `/ajax_novels/chapterlist/{id}.html`; czbooks uses the bare domain only,
  `www` is dead; shuhaige's search backend returns no results).

## What this example shows about the skill

1. **Batch planning:** the three sites came from one ranked shortlist, so
   one research round served three builds.
2. **A real bug found by verification:** the sto9 build failed on-device at
   first because nested `<a>` tags are split by the runtime's HTML parser;
   the fix (pick the first `<a>` with text) was a one-line change, then the
   version was bumped v1 → v2. Without the on-device verification step,
   the bug would have shipped.
3. **A limit honestly reported, not hidden:** shuhaige's search does not
   work because the site's backend returns no results. The extension
   returns a clear Vietnamese error instead of fake results, and the
   limitation is recorded in the repo.
4. **Parallel coordinators, one repo:** two extensions were built in
   parallel by two coordinators pushing to the same `main`. Both did
   `git pull --rebase` before pushing, so there was no conflict and no
   force-push.

## The part that motivated this skill (the failure case)

On 2026-11-07 around 23:30, an Antigravity teamwork run tried to build
three Vietnamese extensions (truyenc, metruyenchu, truyenhoan) plus
sangtacviet directly on the strong model. It died on quota ("Individual
quota reached") after producing only 18 coordination documents and 0 lines
of extension code — no commit, no push. That failure is why this skill
exists: plan with the strong model inside the agent (only a few calls for
planning), execute with the cheap model (which has more quota), and keep
progress in files.
